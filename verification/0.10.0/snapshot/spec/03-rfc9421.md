# 3. HTTP Message Signatures profile

Status: normative design for SAGE `0.10.0`; incompatible with permissive
legacy verifier settings. Historical evidence: `vectors/rfc9421.json` and
`pkg/agent/core/rfc9421/`. Requirements: [R-15 to R-20, R-30, R-34 to
R-36](../charter.md).

## 1. Signature fields and algorithms

**MSG-01 (R-19, R-20, R-34).** A protected HTTP message MUST contain exactly
one `Signature-Input` dictionary member and one matching `Signature`
member, both labelled `sig1`. Parameters `keyid`, `alg`, `created`,
`expires`, `nonce`, `tag` are required, with no duplicate or unknown
parameters. The tag is `sage-0.10.0`. Signers emit parameters in that order;
verifiers MUST reconstruct the received parameter order using RFC 9421,
not regenerate a preferred ordering. `keyid` is an explicit DID key URL
and `alg` MUST equal the selected suite in [chapter 01](01-crypto.md).
Bare DIDs, algorithm guessing and lexicographic signature selection are
not supported.

`Signature` uses the Structured Field byte-sequence syntax and canonical
standard base64. `Content-Digest` MUST be the single member
`sha-256=:<base64 SHA-256 of content>:`. Digests are recomputed over received
HTTP content bytes after transfer framing removal, before JSON parsing.
Content-Encoding, trailers and multipart bodies are not supported in this
profile; senders MUST omit them and receivers MUST reject them.

## 2. Covered components

**MSG-02 (R-15, R-16, R-20, R-34).** Requests MUST cover exactly this list,
in this order (every protected request carries a JSON body):

```
"@method" "@target-uri" "@authority" "content-type" "content-digest"
"x-sage-did" "x-sage-version"
```

`Content-Type` MUST be `application/json` without parameters.
`X-SAGE-Version` MUST be `0.10.0`. `X-SAGE-DID` MUST equal the authenticated
body sender and the DID part of keyid. Receivers MUST compare the target
and authority with their configured receiving endpoint. Untrusted
Forwarded or X-Forwarded headers MUST NOT determine the signed target.
Proxies that change a covered component must operate as explicitly trusted
security endpoints; otherwise alteration fails verification.

**MSG-03 (R-18, R-20).** Responses MUST cover exactly:

```
"@status" "@method";req "@target-uri";req "@authority";req
"content-digest";req "signature";req "x-sage-version";req
"content-type" "content-digest" "x-sage-did" "x-sage-version"
```

The verifier MUST retain the original request components, including its
exact Signature field, and use them for `;req`. Reconstructing a request
from the response is forbidden. `;req` on a request signature is invalid.
Even successful empty application results use a JSON response envelope;
there is no unsigned success or 204 shortcut. The response signer MUST be
the expected request recipient, using a currently authorized key.

## 3. Parsing and verification order

**MSG-04 (R-20, R-30, R-35, R-36).** Receivers MUST enforce a 16 MiB body
limit and a 32 KiB total HTTP field limit before public-key work. Each
signature field is at most 8 KiB. Duplicate instances of Signature,
Signature-Input, Content-Digest, Content-Type and any X-SAGE field MUST be
rejected, rather than comma-joined. Invalid HTTP framing, contradictory
Content-Length/Transfer-Encoding or ambiguous authority MUST be rejected
by the HTTP boundary. Signature bases MUST follow RFC 9421 component
extraction, not ad hoc trimming or URL normalization.

The receiver performs bounded framing/schema checks, checks fixed version,
coverage and timestamp syntax, hashes the body, resolves and validates the
key, verifies the signature, validates the wire envelope, then atomically
checks replay state and authorizes execution. No application side effect
is permitted before every required verification succeeds. Resolver errors,
missing request context and verifier outages are failures, never bypasses.

## 4. Freshness, replay and concurrency

**MSG-05 (R-17).** `created` and `expires` are nonnegative integer Unix
seconds; `0 < expires-created <= 300`. Clock skew allowance is 30 seconds.
Accept timing only if `created <= now+30` and `now < expires+30`.
Clock checks MUST NOT be disabled in production. Trusted UTC time is required; unavailable or uncertain time fails closed. The restart quarantine covers 300s lifetime plus both 30s creation/expiry allowances. `nonce` is canonical
unpadded base64url of 16 CSPRNG bytes. These values MUST equal the body
values. One replay acceptance transaction is shared by HTTP and envelope
validation; validating two signatures on one message is not two requests.

Replay state is keyed by `(sender DID, recipient DID, nonce)`, independent
of key rotation or transport, and retained through `expires+30`. Concurrent
copies MUST have at most one acceptance. Cache exhaustion MUST fail closed.
After lost replay state, an endpoint MUST either recover durable state or
refuse protected messages for 360 seconds before accepting fresh traffic.
Clock rollback that invalidates retention assumptions MUST similarly fail
closed. A retry uses a newly authorized message and nonce; authentication
freshness is not an exactly-once business transaction guarantee.

## 5. Errors and security considerations

**MSG-06 (R-35).** Authentication, policy and replay failures return HTTP
401 with a generic authentication failure; malformed framing or size may
return 400/413 before authentication. Such unauthenticated responses MUST
NOT authorize retries, downgrade or result use. Once peer authentication
succeeds, application failures use a signed response. Local trusted logs
may distinguish causes without recording secrets or full sensitive payloads.

These rules bind HTTP routing in addition to the transport-independent
signature in chapter 08. TLS with server authentication remains required;
message signatures do not conceal content or metadata. A valid signature
alone does not approve a tool operation: the integration profile also applies.

## 6. Sources and follow-up verification

[RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) defines the base
construction and request-bound response components. SAGE fixes its otherwise
application-selected coverage, label and freshness requirements.
[RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html) defines Content-Digest;
SAGE authenticates that field and does not use it as a standalone signature.
The [RFC 9421 errata listing](https://www.rfc-editor.org/errata/rfc9421)
was consulted; errata status and applicability are recorded in the project's
reference review rather than treating reported corrections as accepted.
Existing static vectors do not validate this new profile. Cross-implementation
HTTP base construction, restart races and proxy handling require inspector
execution; no such test was executed in this documentation change.

Errata review (2026-09-13): verified RFC 9421 errata 8102 and 8103
correct the name to `@signature-params`; implementations MUST use that
name under MSG-04. [RFC 9530 errata](https://www.rfc-editor.org/errata/rfc9530)
8158 and 8273 are editorial. Reported 8890 concerns a Brotli example, is
not accepted as a normative amendment here, and is outside the unencoded
content profile.

## 7. Local reference project

The user-designated sibling `rfc9421` repository is an additional source for
RFC text, translations and implementation comparison. See the
[local reference assessment](../verification/rfc9421-reference.md) for snapshot
provenance, build results and departures from RFC 9421. Its current code is not a
conformance oracle; official RFC text and applicable verified errata govern the
base mechanism, while this chapter governs the SAGE profile.
